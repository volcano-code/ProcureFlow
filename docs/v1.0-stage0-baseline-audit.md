### 两类失败的初步根因（尚待修复和重跑）

1. `tests/test_model_acceptance.py` 的 Loopback 协议测试仍把工具集合断言为旧的 3 个工具；当前注册表已包含 5 个只读工具：`get_comparison`、`search_policy`、`get_evidence`、`search_references`、`get_reference_fragment`。六个参数化场景均在同一过期断言处失败。正确修复是更新独立期望并验证五个工具 schema，而不是缩减运行时工具。
2. `test_advice_receipt_survives_logout_but_is_not_disclosed` 的 fake Agent 只返回 `summary`，没有返回任何 `evidence_ids`。当前真实 AdviceService 明确要求引用至少一个已读取的报价证据，因此该 fixture 会触发 `EVIDENCE_REQUIRED` 并保存 FAILED 回执。下一步应让测试 Agent 返回其收到的有效报价证据 ID，再验证登出后结果已持久化但读取仍被拒绝；若修正 fixture 后仍失败，再修复运行时授权/回执逻辑。不得放宽 grounding 规则。
3. PostgreSQL 日志还出现 `uq_one_operation_per_request` 和 `outbox_operation_id_key` 的 duplicate-key 日志，但当前 JUnit 失败列表没有将它们列为失败用例。它们可能来自预期的冲突/并发测试路径，也可能揭示被捕获的异常；目前不能认定为根因。阶段 1 必须关联具体测试、事务结果和 JUnit，确认是否预期，不能仅凭数据库日志判错或忽略。

- 当前 tree 有 14 个 GitHub Actions workflow。
- Alembic 有 9 个 revision，已在本地只读运行 `python -m alembic heads` 和 `python -m alembic history`，确认单一 head 为 `b719aa310001`。迁移顺序为：`426d852ce82c` → `5ce3ab9b84a2` → `a82d71f09c36` → `b9134d27c80f` → `d261a40ce712` → `e731bb62c905` → `f192c4ad8601` → `a40c72de1902` → `b719aa310001`。

## 5. 评测资产边界

- `evals/procurement/development-v1.json` 是 10 个采购建议合成 development 案例；不是 holdout，也不代表真实模型质量。
- `evals/candidate60` 是 60 个公开、开发者编写的合成**候选字段抽取**任务（Dev30 / Validation10 / Evaluation20）。其 README 明确说明它不是 60 个完整采购场景、不是独立人工复核 gold，也不是 unseen Holdout。
- 因此，不能把 Candidate-60 重新命名成 Procurement-60，也不能将两个任务集的数量相加作为采购 Agent 质量成绩。v1.0 仍需单独建立版本化的采购建议端到端任务集，并严格隔离开发、验证和真正未见测试数据。

## 6. 当前文档不一致

当前 README 和威胁模型仍有历史描述：仅 3 个只读工具、没有 AG-UI、没有向量/Hybrid 检索；但当前开发树已加入两个参考只读工具、可选本地 BGE Hybrid 检索和 AG-UI 只读观察器。需要在阶段 1 同步一份当前能力矩阵，同时保留历史阶段文档的时间边界。不能把 AG-UI observer 描述成远程 Agent 执行接口，也不能把本地 Hybrid 检索描述成已通过真实模型答案质量验收。
