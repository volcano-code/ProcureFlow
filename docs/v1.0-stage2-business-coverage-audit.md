## 1. 已有测试覆盖

### 1.1 多商品成本与资格

`services/api/tests/test_multi_item_procurement.py` 已覆盖：

- 每行 Decimal 舍入、绝对折扣、含税/未税处理，以及整单运费只计一次。
- 小数舍入边界（例如数量 × 单价为 0.05 的边界案例）。
- 任一商品行缺少数量、单价、折扣或税率时，整单总价保持未知且不可参与推荐。
- 每行数量、UOM、交期限制；整单预算和租户政策交期上限。
- 空商品篮子、重复 SKU、超过 20 行、标量/多行字段混用、错误类型和歧义合同拒绝。
- SKU 大小写不被折叠，旧单 SKU JSON 序列化形状保持兼容。
- 部分报价、额外报价行、未确认报价不能形成合格方案。
- 完整篮子审批、执行、重复请求只读回原 operation、独立核对和租户隔离。
- 任一需求行、报价行或政策变化使整份审批失效。
- 部分覆盖不能审批或执行。
- 外部写入后回执丢失只做 reconciliation；不确定结果转 NEEDS_HUMAN，不盲目重发。
- Recovery Hold 只允许只读核对，不能释放 Hold 或重放。
- 更换 SKU 身份时，原来源证据不能被新商品借用。

### 1.2 多行 CSV/XLSX 导入与来源完整性

`services/api/tests/test_multi_item_imports.py` 已覆盖：

- 多行报价映射、逐单元格来源坐标、文件 SHA-256 和稳定 fragment ID。
- 运费作为报价级字段只计一次，不从多行累加。
- XLSX 公式不执行、不使用公式缓存值；不同工作表来源相互隔离。
- 混合供应商、币种或运费表头拒绝；全缺失字段继续保持未知。
- 重复 SKU、额外 SKU、歧义 SKU、不支持 UOM 拒绝。
- 缺失数量/单价/税费/折扣不被补零，阻止比较与推荐。
- 部分行可以导入查看，但不具备完整报价资格。
- 无效行选择、超过 20 行、重复行和不合法映射不改变数据库状态。
- 需求/预览 revision 变化导致旧预览失效；并发重复确认只创建一份报价。
- 预览跨进程重启可读取；原文件篡改后拒绝预览和确认。
- 20 行报价可导入；第 21 行不会被隐式纳入。

### 1.3 政策与审批约束

`services/api/tests/test_policy_adversarial.py` 已覆盖租户/角色隔离、政策发布并发版本冲突、预约生效顺序、不同供应商数量去重、租户政策上限不能放宽需求上限、未选中报价变化导致历史快照失效、建议运行中政策版本固定、预约政策生效时阻止不再授权的外部写入，以及并发服务初始化。

### 1.4 已有独立采购建议开发集

`evals/procurement/development-v1.json` 有 10 个冻结合成案例，覆盖正常选择、未知运费、税价模式、预算、交期、数量、折扣、证据冲突、标识符大小写和不可信来源指令。它通过真实 ProcurementService、AdviceService 和 LangGraph 运行时执行，但 Provider 响应是合成 Fixture；报告明确保留 `usage_is_synthetic=true`、`cost=null`、`semantic_factuality_verified=false`。它是开发集，不是盲测或真实模型成功率。

## 2. 业务范围边界

- 请求支持 1–20 个唯一、区分大小写的 SKU；币种 CNY、单位 EA。没有多币种换算、单位换算、拆分供应商 award、替代品或部分采购。
- 多行比较和 MockERP 可以覆盖税费/折扣；当前真实 ERPNext 多商品映射合同更窄，要求明确零税率、零折扣、共同税价模式、整数 EA 数量及金额上限。超出映射范围必须在网络写入前拒绝，不能把 MockERP 的能力写成 ERPNext 全范围支持。
- 20 行导入测试证明映射器支持 20 行，不等于 20 行从导入、确认、成本、审批、ERP 草稿到独立回读的完整端到端已通过。
- 工程测试覆盖不等于 Agent 的真实决策质量；不能把 Candidate-60 字段抽取任务当成 Procurement-60 采购决策任务。

## 3. 阶段 2 尚需补齐的验证

1. **20-SKU 全链路**：增加一个 20 行请求从多行来源导入、逐行确认、比较、审批、MockERP 写入到独立读回的完整端到端用例；同时证明缺失/重复/额外行不会写入。
2. **独立多商品 Oracle**：为多商品金额、资格和来源绑定建立手工冻结的 expected JSON，评分器不得调用生产计算器生成期望值；至少覆盖 1、2、20 SKU，税价模式、折扣、运费未知、舍入边界和行身份替换。
3. **ERPNext 映射负向矩阵**：在隔离、一次性 ERPNext sandbox 中验证当前支持的零税率/零折扣路径，并验证非零/混合税、折扣、分数 EA、币种/UOM 不匹配在任何 POST 前被拒绝。不得使用用户真实 ERPNext 凭据或生产实例。
4. **全量业务回归绑定**：为每次 RC 变更保留 core、PostgreSQL、browser、Compose、ERP sandbox 对应同一 commit/tree 的报告；SQLite 与 PostgreSQL 的结果分别记录。
5. **历史兼容**：确认单 SKU 合同/历史快照仍按旧版本解释；不得让多 SKU 字段改变旧数据语义。

## 4. 当前结论

现有确定性业务测试已覆盖多商品计算、导入来源、审批快照、幂等和恢复的主要风险，不能将其描述为“业务内核尚未实现”。阶段 2 的剩余工作应集中在**20-SKU 完整端到端、独立多商品 Oracle、ERPNext 映射负向矩阵和精确提交证据**，而不是重写现有成本或政策模块。

本审计不声明这些新增门槛已运行。新增测试必须先提交，再以同一确切提交的 CI/隔离 sandbox 结果验收。真实模型质量、采购 Holdout、独立语义评审和生产安全仍属于后续阶段。


## 5. RC1 implementation progress (2026-11-17)

The following Stage 2 work has now been committed on the RC branch. These are implementation records; the newest commit's CI is still required before marking the tests as passed.

### 5.1 Maximum-size end-to-end basket

Added `test_twenty_item_import_to_verified_draft_end_to_end` to `services/api/tests/test_multi_item_imports.py`. It creates a 20-SKU request, imports 20 explicit CSV rows, checks per-line source fragments and shared freight provenance, confirms the quotation, computes the proposal, obtains independent approval, dispatches a MockERP draft, checks 20 persisted lines and performs auditor readback.

The first run exposed a fixture defect: the test used supplier `SUP-20`, which is not in the deliberately seeded MockERP directory. The observed result was `NEEDS_HUMAN / UNKNOWN_SUPPLIER`; this was not a product-calculation failure. The test now uses the existing seeded synthetic supplier `SUP-A`. It still exercises the 20 distinct SKU identities. This exact correction must pass both core and PostgreSQL integration jobs before it is accepted.

Frozen expected outcome: goods CNY 200.00 + gross freight CNY 7.00 = CNY 207.00. All 20 item rows must be present in the independent MockERP readback; one operation and one draft only.

### 5.2 Frozen independent deterministic oracle

Added `evals/procurement/multi-item-oracle-v1.json` and `services/api/tests/test_multi_item_oracle.py`. Six hand-authored cases cover:

1. mixed included/excluded tax, line discount and quote-level freight once;
2. per-line ROUND_HALF_UP boundary rounding before aggregation;
3. inclusive tax not added a second time;
4. unknown freight blocks total while retaining known line subtotals;
5. unknown line price blocks the whole basket total;
6. unsupported currency remains non-comparable.

Expected totals and line components are literal frozen values in the JSON fixture. The test does not call the production calculator to generate its expected results. This is a deterministic calculation oracle, not an Agent task set or real-model benchmark.

### 5.3 ERPNext mapping negative matrix

Extended `services/api/tests/test_erp_cost_mapping.py` with a supported multi-item zero-tax/zero-discount mapping test and pre-network rejection cases for:

- positive line tax, line discount, mixed tax modes, non-EA unit, missing explicit tax rate;
- unsupported currency and unknown freight;
- fractional quantity and unit/ freight amount bounds;
- payload total mismatch, duplicate SKU and missing freight account.

The tests call the real `ERPNextClient.create_draft` boundary with a transport that fails if any HTTP request is attempted. For every unsupported input, the expected `ERPRejected` code must occur while the captured network call list remains empty. A zero-freight supported basket must not require a freight account.

This matrix tests the adapter's pre-network guard. It is not a live ERPNext roundtrip; disposable ERPNext sandbox and independent MariaDB readback remain separate gates.
