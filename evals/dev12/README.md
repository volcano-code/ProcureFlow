## 协议与评分

`evals/baseline.py` 只接收 TaskBundle 公共输入，不读gold，不按category查表返回答案。
它调用原来的 ProcurementService：创建临时需求、导入文件、程序模拟确认原提取字段（不修改）、analyze。
报价行号直接回指输入原文。仅将既有错误码规范成稳定 issue 名称；不添加新版引用识别或制度检索来偷偷改善基线。

判定器 `evals/devbench.py` 不导入生产解析器/计算器/服务，也不用生产算法重新生成金标准。
金额参考是冻结常量。逐题严格检查全部关键字段、总额、选中报价、结果状态、问题集合、引用文档/版本/哈希/行/原文和禁止副作用。
输出 `execution_complete` 与 `all_tasks_passed` 分开；未支持的题留在分母，缺整题也不剔除。
同一报告只能包含一个runner、一个attempt、每题一条记录。重复试验不能用“最好一次”替代首轮成功。
输入清单、原文件、实现源码均有摘要绑定；Gold摘要在评分阶段另行绑定。

`critical_field_exact_match` 的分母是金标准中127个可回答关键字段，而不是模型愿意回答的字段。
引用位置有效性只针对提交过的引用；未提取字段会降低字段覆盖和严格任务成功率。
`semantic_support_rate` 始终为null：没有把“行号存在”冒充通用自然语言语义支持评测。
费用保持null；本轮无真实模型usage/价格/账单。

## 运行与结果解释

使用根README中的 `validate → predict-baseline → grade` 命令。
`predict-baseline`不读取gold；可移走gold目录验证这一边界。
观察文件和分数文件只允许新建，不静默覆盖先前记录。
默认grade退出0仅表示评测已执行，不能作为所有题通过的徽章。
要求严格全过时增加 `--require-all-success`；已有基线应退出1。

本轮观测到的A基线为7/12，5题未通过（含2题不支持）。003/004自然语言解析缺失，
008未识别新版替代，009/010未执行有效制度判断。详细分数必须取同次源码指纹对应的真实输出。
`self-check`的12/12仅检验参考答案形状与评分器一致性；不构成独立效果证据。

## 安全和使用范围

评测使用一次性SQLite和拒绝写入的ERP对象，不创建审批/执行任务，不调用模型。
服务包装层对approve/enqueue/process_operation/edit_quote调用直接失败；原有模拟确认必须显式披露。
这是受控离线域服务测试，不是操作系统网络沙箱、安全认证、真实人审批、原生UI或ERP联合测试。
未来B/C模型方案需要独立runner、真实调用记录与相同证据权限/预算；当前没有用mock模型占位冒充完成。
